EIS OneSuite infrastructure, in one tree

The iac directory is not a repository. It is a workspace holding about 60 independent GitLab repos that together build, ship and run isolated OneSuite environments for EIS clients: Terraform modules and templates, one repo per client environment, an ArgoCD hub for Kubernetes workloads, Ansible for the CI/CD toolchain VMs, and a Claude Code harness that guards all of it.

62 nested .git dirs 35 eis-* modules 4 Terraform templates 12 Terraform project repos 10 clusters on the hub 39 Argo components

What this is and how to read it

Every directory with a .git inside it is its own project in GitLab group iac (id 1711). Run git, glab, MRs and Atlantis inside the nested repo, never at the root. Launch claude from the root so the project harness in .claude/ is active. Everything needs the VPN: a GitLab hostname that returns NXDOMAIN means the tunnel is down.

Source of this page. Four read-only sub-agents surveyed the tree against disk and the root docs. Tags and branches come from local clones, nothing was fetched, and several clones sit on feature branches. Where a claim could not be confirmed on disk it is called out. Section "Known drift" lists where older docs disagree with disk.

Build

Reusable Terraform modules and Copier templates turn into one Terraform repo per client environment. Atlantis plans and applies from merge requests.

Run

Kubernetes workloads come from one ArgoCD hub, which pulls from Git. VM toolchains (Jenkins, Nexus, Sonar, Atlantis) are configured by Ansible over SSM.

Guard

A Claude Code harness blocks local applies, merges, secret leaks and raw AWS resources, and forces verification before work is called done.

How the pieces fit

Three delivery paths share the same GitLab group. The Terraform path creates AWS infrastructure. The GitOps path puts workloads on the clusters that path creates. The host path configures the EC2 toolchain machines.

Conventions shared by the modules

  • Scaffolding: 32 of 35 come from the module Copier template. eis-argocd, eis-fivetran-hybrid and eis-ec2-rhel-ami do not and have no release job.
  • Toolchain: Terraform >= 1.13, AWS provider ~> 6.0, inputs project_prefix and tags, docs generated by terraform-docs.
  • Release: a manual publish_release job runs semantic-release. feat is minor, fix/chore are patch, docs does not release.
  • Quality gate: pre-commit only (validate, fmt, tflint, checkov, terraform-docs). No module has tests, examples or a changelog.
  • Commit lint: type(scope): TICKET-N - message, with TICKET in COEXT, GENESIS, NOJIRA or EISSAASDEV. Most rendered modules reject EISSAASDEV and the ! breaking marker, so use a BREAKING CHANGE: footer. Check each repo's own .pre-commit-config.yaml.
Module rule for consumers. New AWS infrastructure in a client repo must come from an eis-* module, not a raw resource "aws_*" or registry module. A harness hook denies new raw blocks. If no module exists, wrap the upstream one as a new eis-* module first.

Copier templates and the client repo

All four Terraform templates use [[ ]], [% %] and [# #] as Jinja delimiters so HCL ${} survives. A consumer records the template version in .copier-answers.yml (_commit); copier update does a three-way merge and Renovate opens the update MRs.

Anatomy of a rendered client repo (credit-agricole)

lower/infra/{bootstrap,core,services}   shared services stage, lower account
lower/dev/{core,services}   lower/test/{core,services}
upper/share/{bootstrap,core,services}   upper/stage/...   upper/prod/...
atlantis.yaml   .gitlab-ci.yml   .pre-commit-config.yaml   ci/generate-atlantis-projects.sh
global.tfvars per stage (rendered once, never overwritten)
  • Three words: level is lower or upper (account and region), stage is infra|dev|test|share|stage|prod, state is bootstrap|core|services. Each state is one Terraform root and one Atlantis project.
  • State: S3 with use_lockfile, no DynamoDB, one bucket per level or stage. Cross-state reads use tag-based data sources, not terraform_remote_state.
  • Atlantis order: project <level>-<stage>-<state>, execution group stage_index*10 + state_index. automerge and parallel runs are off.
  • Customising: put changes in *_custom.tf or *_override.tf, which Copier never overwrites, and record an ADR.
  • CI: one pre-commit job plus a manual publish_release that exists only in the template. It rewrites both GitLab hostnames with the job token so git:: modules download.

Network hub

One account (nhub) owns a Transit Gateway per region, shared to client accounts through RAM. Clients attach as spokes and find hub resources by tag:Name. The rule from the project instructions: the hub region owns egress and the corporate S2S VPN, and satellites never do.

RegionFlavorEgressCorporate VPN
us-west-2primary hand-maintained, not a renderNetwork Firewall (alert-only), NAT, IGWOwn tunnels, propagated to peering
eu-west-3regional hub "island"Local firewall and NATOwn tunnels, not propagated
ap-northeast-1satelliteNone locally; default route goes over TGW peering to the primaryNone

The ASN scheme is 65050 + 2 * region_code. Apply the primary core first, then each core-<region>, because peering looks up the primary by tag.

ArgoCD

The hub is aws0iacdeveks01 in the eis-iac account. Argo CD there is the EKS-managed capability, created in projects/aws/eis-iac/terraform/lower/dev/services/argocd.tf, not a self-hosted install. It does not register clusters on its own, so each spoke has a cluster-secret-*.yaml under bootstrap/clusters/aws0iacdeveks01/manifest/. Git access goes through AWS CodeConnections.

Layout of argocd/argocd

apps/app-of-apps.yaml        applied once by hand, points at apps/appsets
apps/appsets/                all-components, cluster-bootstrap, playground-components
bootstrap/clusters/<hub>/    Argo control-plane config: AppProjects, cluster secrets, argocd-cm
clusters/<cluster>/          cluster-component-config.yaml, values.yaml, one dir per component
components/                  39 Helm chart dirs     components-playground/  35 dirs
  • One Application per cluster and component. The all-components ApplicationSet matches each cluster's config file against its component directories and requeues every 120 seconds. A cluster is a directory; adding a cluster needs no appset edit.
  • Value precedence (last wins): component default, cluster-wide values.yaml, per-component values.yaml.
  • Sync waves order resources only inside one Application. Retries (16 attempts, up to 60s backoff) absorb the secret-store then CRD ordering on cold clusters.
  • Placement rule: workloads go in components/; Argo control-plane config goes in bootstrap/.
  • Secrets: External Secrets Operator reads Secrets Manager (6 clusters) or Vault.

Onboarding a cluster

  1. On the spoke, Terraform adds an EKS access entry for the Argo CD role.
  2. Generate clusters/<slug>/ with the argocd/template/clusters Copier template. tools/answers.py discovers about 20 answers from live AWS and also writes the bootstrap files and the cluster secret.
  3. Merge the MR. CI renders every cluster and component (kubeconform, kube-linter, pluto, checkov). Argo then creates the Applications.

Nothing here is applied by hand. The pipeline has no apply step; delivery is Argo pulling the default branch. Spoke clusters are private, so cluster state cannot be checked from a laptop.

Fleet drift. The cluster template is at V2.1.2, but cluster answers files are pinned across V1.0.5 to V2.1.2. Six clusters are still on V1.0.5.

Ansible

Ansible configures the CI/CD toolchain VMs a client gets in the infra stage. It reaches hosts through the aws_ec2 inventory plugin and the aws_ssm connection, so there is no SSH to targets. Secrets come from Vault lookups at runtime. On macOS, run it through ./docker/run.sh.

The client template (v1.5.1 on local main) renders playbooks for Jenkins, GitLab, Nexus, Sonar, Atlantis, Keycloak, Sisense and more, each behind an enable_* toggle, plus a kernel-patch playbook with snapshot, patch, reboot and verify. Many roles come from the older cv-devops GitLab group and are not cloned here.

Lower and upper split is not released. The template's lower/upper inventory split lives on the unmerged remote branch COEXT-108807_ansible-template-level-split. Main is single-level, and local main is behind the v1.5.2 Podman tag.

How a change ships

The agent does the work up to the plan review. You apply and merge. Both are blocked for the agent by hooks.

StepWhoWhat happens
1. BranchagentFrom explicit origin/main, in the nested repo or a worktree. One MR, one Jira ticket.
2. Edit and plan locallyagentModule-first hook active. Read the plan lines, not the summary.
3. CommitagentMessage must match the repo's lint regex. Stage explicit paths, never git add -A.
4. Pre-pushagentRun gitlab-ci-local (local pre-commit is not equivalent), then verify-iac-changes. A hook re-lints commits and runs pre-commit on the diff.
5. Open MRagentReviewer eramadan. Atlantis autoplans and comments.
6. Read the planagentTag each change as MR-caused or environment-carried. Check destroys and "forces replacement". Cite live aws output.
7. Hand backagentStop. Give paste-ready text with Disruption: NONE|BLIP|OUTAGE - evidence - window: yes/no.
8. ApplyyouComment atlantis apply on the MR, wait for green, test live.
9. MergeyouMerge after apply, not before. The Atlantis lock holds until merge.
10. AfterbothA module repo publishes a tag, then a consumer bump MR follows.

Exception: eis-iac/terraform has no Atlantis. There you run terraform plan -out and apply the saved plan file yourself, always with -target, never -auto-approve. A full plan there strips tags and rolls AMIs.

Guardrails in .claude/

Eight hooks are wired plus a session-start check, three path-scoped rule files (terraform, argocd, ansible) and four read-only subagents. About 100 user skills live in ~/.claude/skills; the root CLAUDE.md has a routing table that names the skill for each kind of task.

HookFires onEnforces
guard-bashBash, beforeDenies local terraform apply outside eis-iac, -auto-approve, MR merge, posting atlantis apply, plaintext tokens, push to main, force-push, bare push, recursive rm in the tree, git at the wrong root, Jira and Slack writes.
guard-mcpMCP, beforeDenies outbound sends (Slack, Jira, Gmail) and destructive mailbox or file operations.
pre-push-checkBash with git pushLints every new commit message, runs pre-commit on the diff, runs the module-first check. It does not run gitlab-ci-local.
eis-module-guardWrite, EditDenies newly added raw aws_* resources and non-eis modules in consumer repos.
verify-gateStopRuns the fast scanner lane (tflint, checkov, kube-linter, gitleaks) on edited repos and blocks on findings.
handoff-gateStopBlocks an atlantis apply handoff that lacks the Disruption line.
track-edits, classify-failureAfter edit, after failureRecord edited repos; route failures to the right skill (lock, 403, SSO expired, VPN down).

The four subagents are iac-live-verifier (proves live AWS and GitLab state), iac-planner, mr-reviewer and tf-plan-auditor. bash .claude/harness.sh selftest checks the guards, and harness.sh eval replays an adversarial corpus through the real hooks. Escapes exist (HARNESS_SKIP_VERIFY=1, HARNESS_SKIP_PRECOMMIT=1) for the user to set, not the agent.

Glossary

OneSuite
The EIS application suite delivered per client. "Platform" here means the isolated AWS stack that hosts one client's copy.
COEXT, GENESIS, EISSAASDEV, NOJIRA
Jira project keys allowed in commit messages. COEXT is cloud-ops requests, GENESIS is platform and tech-debt work, EISSAASDEV is SaaS delivery. NOJIRA is the placeholder.
Atlantis
Terraform automation on GitLab MRs: plans on open, applies on an atlantis apply comment. One lock per project, directory and workspace until merge.
Lower / upper
In client Terraform, lower is the non-prod account (infra, dev, test) and upper is the prod-tier account (share, stage, prod). In the Ansible template branch, lower is the infra tier and upper the app tier.
Hub / satellite
Network hub region owns egress and VPN; a satellite region routes through it. Separate from the "ArgoCD hub", the EKS-managed Argo CD that manages the spoke clusters.
CAA, NNLJ, AXAJP
Credit Agricole, NN Life Japan, AXA Japan. Region codes: aws0 us-west-2, aws06 ap-northeast-1, aws11 eu-west-3.
IdC
AWS IAM Identity Center, used for human access and as the SAML source for Cognito.
ESO
External Secrets Operator. Copies Secrets Manager or Vault values into Kubernetes Secrets.
IRSA
IAM Roles for Service Accounts. Gives a pod an AWS role, for example for OpenSearch SigV4 or Velero.
TGW / RAM
Transit Gateway, and Resource Access Manager, which shares it with client accounts.
Copier
Template engine behind the client, module, hub, ArgoCD-cluster and Ansible templates.
CI3.0 toolchain
GitLab, Jenkins, Nexus, Sonar, OpenGrok, Atlantis, Keycloak, Sisense and Selenoid hosts, deployed as EC2 machines per client.
Harness
The project's Claude Code guard setup: hooks, deny and ask lists, rules, subagents, selftest and eval.
