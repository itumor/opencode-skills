# EIS build/deploy host provisioning + EKS access

## What it is
EIS client accounts put **all build/CI/deploy EC2 hosts in the shared `infra` stage** (`projects/aws/<client>/terraform/lower/infra/services/`), NOT in the target stage's VPC. `lower/<stage>/services` has eks/rds/msk/s3 but **no ec2 module**. A "build host for UAT/<stage>" therefore = a new instance in `infra/services`, reaching the target cluster over the existing TGW path. Hosts are SSM-managed RHEL; deploy tooling typically runs in pipeline containers, so the host itself usually needs only base RHEL + SSM + (maybe docker) + an EKS access entry — confirm scope with the requester (infra/access vs full ansible config).

Reference impl (live 2026-06-15, COEXT-105506, CAA MR !76): dedicated UAT deploy host `aws0caaudep01` cloned from the shared `bld01` config, UAT-scoped IAM, cluster-admin on `aws0caatesteks01`.

## Workflow
1. **Check if a shared host already serves the target.** The existing `bld01`/`jnk01` group IAM often already covers all clusters (`<prefix>eks*`/`deveks*`/`testeks*`) and the cluster's `access_mapping` may already map `ec2_group=bld`. Verify live: `aws ec2 describe-instances --filters Name=tag:Name,Values=<prefix>bld01`, `aws eks list-access-entries --cluster-name <cluster>`. If a **dedicated** host is still wanted (manager's call), continue.

2. **Pick a collision-safe acronym** (see Gotcha 1). NOT `ubld`/`uatbld` (contains `bld`). Use e.g. `udep` (UAT deploy). Instance key `<acronym>01` → `<prefix><acronym>01`, role `<prefix><acronym>01-Role`, group policy `<prefix><acronym>-Policy`.

3. **Terraform `lower/infra/services/`** (mirror the CyberArk/CUSTOM-marker convention — `ec2_settings` is a template-owned var, edit inline with `# BEGIN/END CUSTOM <id> | <JIRA>` blocks):
   - `variables.tf` `ec2_settings.<acronym>` — clone `bld` (enable_policy, m6a.xlarge, `root_block_device {volume_size=300, volume_type="gp3", encrypted=true}`, `custom_rules=["30000-30010/tcp"]`, `additional_prefix_lists=["workspaces-dev"]`, Backup tag). **`encrypted=true` is safe on a fresh host** (no existing volume to flip false→true → no replacement).
   - `terraform.tfvars` `ec2` map: `<acronym>01 = {}` (all behaviour merges from settings).
   - NEW `files/iam/ec2/<acronym>.json` — **stage-scoped** least-privilege: EKS + Secrets limited to `<prefix><stage>eks*` (e.g. `testeks*`) only (drop the all-clusters breadth of `bld.json`), ECR push/pull, S3 `<prefix>*portal-*`. Rendered via templatefile vars `project_prefix/account_id/region`.

4. **Terraform `lower/<stage>/services/terraform.tfvars`** — add a NEW key to `eks["01"].access_mapping` (non-destructive; leave existing `ci`/`ci-etcs` alone):
   ```hcl
   "ci-uat" = { ec2_group = "<acronym>", policy = { arn = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy", scope = "cluster" } }
   ```

5. **Ordered apply** (Gotcha 2): `atlantis apply -p lower-infra-services` → re-`atlantis plan -p lower-<stage>-services` (now shows `+ aws_eks_access_entry` + `_policy_association` for the new role) → `atlantis apply -p lower-<stage>-services` → merge. A plain ordered `atlantis apply` works because exec-order puts infra (13) before stage (33); a targeted stage-first apply silently skips the access entry.

6. **Ansible host-config** (`projects/aws/<client>/ansible`) — group_vars/`<acronym>`.yaml + add acronym to `playbooks/linux_joindomain.yaml` `hosts:`. `environment`/`docker_install`/`vault_agent` are `hosts: all` so `-l <host>` picks the new host up. **Often deferred / SSM-only** — confirm whether the host needs domain-join + docker, or if pipeline-container tooling suffices.

## Gotchas
1. **eis-eks `ec2_group` is a SUBSTRING matcher.** `eis-eks/data.tf`: `data.aws_iam_roles.ec2_group` uses `name_regex = ".*${ec2_group}.*"`. So an acronym containing an existing `ec2_group` value (`bld`, `jnk`) double-binds: e.g. `ci={ec2_group:"bld"}` would resolve BOTH `bld01-Role` and `ubld01-Role` → EKS rejects two access entries for one principal → **apply fails**. Grep the chosen acronym vs every existing `ec2_group` both ways before committing.
2. **Empty-lookup ordering trap.** The `access_mapping` `ec2_group` lookup runs at PLAN time. If `lower/<stage>/services` plans before `<acronym>01-Role` exists, the access entry is **silently not created** (no error) — you'd need a second apply. Always create the host (infra) first, then re-plan the stage.
3. **CI pipeline red with green pre-commit** = the GitLab pipeline's `external` stage carries Atlantis commit statuses (invisible to the REST jobs API). See atlantis-debug skill / Gotcha in that skill.
4. **`update-kubeconfig` AccessDenied on `eks:DescribeCluster` despite the policy listing it** = malformed cluster ARN in `files/iam/ec2/<acronym>.json`. EKS cluster ARN is `cluster/<name>` (slash), NOT `cluster:<name>` and NO `/*` suffix. The template's `bld.json` shipped `cluster:${project_prefix}deveks*/*` (dead — pattern never matches), while `jnk.json` was correct. Grep `:cluster:` in the host's IAM json. Fix = `cluster/${project_prefix}deveks*`. Immediate bypass (no IAM change): `aws eks get-token` does NOT need DescribeCluster — hand-build kubeconfig with embedded `server`+`certificate-authority-data` + exec `eks get-token`. See [[eks_cluster_arn_separator_iam]] (axajp MR !9, template MR !27).

## E2E verification (SSM, no ansible needed)
Prove the host authenticates to the cluster as the access entry grants. SSM `AWS-RunShellScript` on the instance:
- Install tools: `dnf install -y unzip`; aws-cli v2 (`awscli.amazonaws.com/awscli-exe-linux-x86_64.zip` → `./aws/install --update`); kubectl (`dl.k8s.io/release/v<clusterver>.0/bin/linux/amd64/kubectl`). Egress for both is usually open via TGW (`eks.<region>` 403 = reachable).
- **Trap: SSM root shell `$HOME` ≠ `/root`** → kubectl hits `localhost:8080`. Export `KUBECONFIG=/root/.kube/config` (and `HOME=/root`) explicitly after `aws eks update-kubeconfig --kubeconfig /root/.kube/config`.
- Proof commands: `aws sts get-caller-identity` (= `<acronym>01-Role`); `kubectl auth can-i '*' '*'` → yes; `kubectl get ns` (target ns Active); `kubectl get nodes`; `kubectl auth can-i create deployment -n <target-ns>` → yes; `kubectl create configmap x --from-literal=a=b -n <target-ns> --dry-run=server -o name` (real write authz, not persisted); `kubectl auth whoami` → `Extra.sessionName = <instance-id>` (cluster sees the host).
- **Cleanup after test** (if ansible/host-config is deferred): `rm -rf /root/.kube /usr/local/aws-cli /usr/local/bin/aws /usr/local/bin/aws_completer /usr/local/bin/kubectl` to leave the host pristine for the team's own config.
- No-host network-only proof: `curl -sk <api-endpoint>/version` from the host → HTTP 401 = TLS + reachable via TGW + control-plane SG (which admits the `local` prefix, 10/8 ⊇ infra subnets).

## Tooling persistence — DON'T over-clean a host people will actually use (COEXT-105506, 2026-06-17)
The E2E "cleanup after test" above is **only** correct when the team will run their own config that installs deploy tooling. A bare deploy host — aws-cli/kubectl removed, nothing in the ansible `bld` config installs them — leaves real users hitting **`aws: command not found`** the first time they SSM in (vfiasko, COEXT-105506). The bld ansible role does NOT install aws-cli/kubectl. So:
- If the host is a deploy host people log into and run `aws eks update-kubeconfig`/`kubectl`, **keep the tools** — install aws-cli v2 + kubectl **system-wide to `/usr/local/bin`** (root, via SSM) so every login user inherits them. Durable answer = add both to the bld ansible role (idempotent), else a manual `/usr/local/bin` install dies on host replacement.
- **Stale-shell trap:** if you install the binaries *after* a user already opened a shell, their pre-install login session caches the negative lookup → still `command not found`. Fix in that shell: `hash -r` or reconnect. `/usr/local/bin` is on the RHEL default login PATH (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`) for **all** users identically — a per-user difference is almost always one user on a stale shell, not a PATH/permission issue. Verify with `su - <user> -c 'echo $PATH; command -v aws'`.
- **Shared instance-role creds:** the host's EKS access comes from the EC2 instance role via IMDS, so **any** user who can log in inherits the same cluster access (cluster-admin here) with no `--profile`. Expected for a shared build/deploy host — if per-user isolation is required, that's a different design (don't grant cluster-admin to the instance role).

## Full build toolchain (java/maven/ant/helm + aws-cli/kubectl) — the `build_node` role set (COEXT-105506, E2E 2026-06-18)
Beyond aws-cli/kubectl, a real Jenkins build/deploy host needs **java + maven (+ ant/helm)**. Source = the EIS role **`cv-devops/ansible/ansible-roles/build_node`** ("Build Server for Jenkins v12/v20"; deps `environment`+`cli_tools`+`openjdk_install`+`docker_install`). The reference host `aws0caabld01` was originally built by the legacy `cv-devops/ansible-bundles/build-srv` submodule bundle (Temurin tarball→/opt).
- **Root-cause pattern:** a host stood up in a NEW VPC with only `environment`+`docker_install`+`linux_joindomain` is MISSING the whole toolchain → `java: command not found`, Jenkins agent dies on `/opt/jdk21/bin/java`. Quick check: `/etc/profile.d/` has no `jdk.sh`/`maven.sh`/`ant.sh`. SSM-inventory the reference host for exact versions: `for b in java mvn ant helm aws kubectl; do command -v $b && $b --version; done; ls /opt`.
- **To reproduce the reference host EXACTLY, use the STANDALONE roles, not `build_node` v_20** — `build_node` v_20 installs java via dnf openjdk (→ `/usr/lib/jvm`, wrong path). `temurin_openjdk` downloads the Temurin tarball to `/opt` + makes the **`/opt/jdk21` symlink** + `profile.d/java.sh` → satisfies Jenkins' hardcoded `/opt/jdk21/bin/java`.
- Vendor into the client ansible `roles/requirements.yml`, pinning tagless roles to a commit SHA: `temurin_openjdk`, `maven`, `cli_tools` (v1.0.1); `ant_install` usually already present. Use host `sfo-devopsgit01:2224` (the one `run.sh` ssh-keyscans). New `playbooks/build_node.yaml` → `hosts: bld`, `become: true`, roles `[temurin_openjdk, maven, ant_install, cli_tools]`; **apply `--limit <host>`** so the shared bld01 isn't touched.
- **`cli_tools` installs aws-cli (toggle `aws: true`) + kubectl + helm** (kubectl/helm default-on); set `kubectl_version` to the cluster minor.
- `group_vars/bld.yaml` pins (match reference): `openjdk_version: "jdk-21.0.5+11"`, `set_java_as_default: true`, `maven_version: "3.8.9"` + **`maven_download_url` → `archive.apache.org`** (role default `dlcdn.apache.org` 404s archived versions), **`set_maven_as_default: true`** (default false → no `/usr/bin/mvn` → `mvn: command not found`), `ant_version: "apache-ant-1.9.16"`, `aws: true`, `helm_version: "v3.12.0"`. Optional `/opt/maven` symlink (play `post_tasks`) — the maven role only makes `/usr/bin/mvn`, but a Jenkins Maven-tool home may point at `/opt/maven`.
- **E2E** as the real login user (`su - <build_user> -c '…'`, loads profile.d): `java -version`=21.0.5 + `/opt/jdk21/bin/java -version`, `mvn -v`=3.8.9, `ant -version`, `helm version`, `aws --version`, `kubectl version --client`, then the cluster repro `aws eks update-kubeconfig … && kubectl get ns`. Re-run playbook → idempotent. Reference: CAA ansible MR !16. Reviewer = eramadan (ansible).

## Wiring the bld host into Jenkins as an SSH agent node (manual) — host-key trap (COEXT-106273)
The Jenkins controller reaches the bld host as an **SSH build agent**, and that node is configured **by hand** in Manage Jenkins → Nodes — it is NOT in JCasC. `casc_config.yaml.j2` has no `jenkins.nodes:`/`launcher` block; the `security.gitHostKeyVerificationConfiguration` stanza there is **git-client-plugin (git checkout) only** and does NOT govern the ssh-slaves agent launcher. So a fresh OneSuite Jenkins has no agent node until someone adds it, and every connection knob below is a per-node manual choice (which is why CAA and axajp behave differently with identical ansible).
- **Connect-user** is per-node (see [[onesuite_keyless_ad_build_agent]]): keyed hosts (CAA) → `ec2-user` + keypair credential; **keyless hosts (axajp)** → AD build SA `<code>_build` (e.g. `axajp_build`) with a **username/password** credential (AD password; bld needs `PasswordAuthentication yes` + SSSD resolving the user). Stack-trace `TrileadSSHPasswordAuthenticator` = password cred in use.
- **THE TRAP — agent dies `Key exchange was not finished, connection is closed.`** preceded by `[SSH] No Known Hosts file was found at /var/jenkins_home/.ssh/known_hosts`. Root cause = the ssh-slaves launcher defaults to **"Known hosts file Verification Strategy"** and the controller has no `known_hosts` for the bld host → host-key verifier rejects **mid-KEX**. Log ORDERING proves it (verifier message before the KEX-fail = KEX algorithms negotiated + host key received, then rejected) → do NOT chase KexAlgorithms/Ciphers/MACs crypto or RHEL9 strict-policy. Not an auth failure either (never reaches auth).
  - **Fast fix (Jenkins UI, no shell):** Node → Configure → Launch agents via SSH → **Host Key Verification Strategy → Non verifying Verification Strategy** → relaunch.
  - **Secure fix (needs controller shell):** `docker exec -u jenkins <jenkins-ctr> bash -lc 'mkdir -p /var/jenkins_home/.ssh && ssh-keyscan -H <bld-fqdn> >> /var/jenkins_home/.ssh/known_hosts'` → relaunch.
  - **Durable (codify in `docker_compose_jenkins`):** seed known_hosts at provision (ssh-keyscan the bld host), or declare the node in JCasC `jenkins.nodes:` with explicit `launcher.ssh.sshHostKeyVerificationStrategy`. Today hand-clicked → fresh envs fail on the default; reviewer = eramadan (ansible).
- **Jenkins admin login** (to reach the Nodes page): AD realm — use your own AD account if in an admins group (`DevOps`, `EISCITEAM`, `EIS Tier1-Support`, `Genesis_DevOps_CI`, `soc-team`). Shared fallback = internal user `jenkins_fallback`, password at Vault `secret2/data/<project>/automation/jenkins:JENKINS_PASSWORD` (user key `:JENKINS_USERNAME`). AD bind/group + admin-cred vars live in `docker_compose_jenkins/defaults/main.yml` (`ad:`, `jenkins_admin_username/password`, `fallback_user`).
See [[coext106273_jenkins_bld_knownhosts_kex]].

## Variant: host INSIDE the stage VPC, test/services-owned (COEXT-105506, RESOLVED 2026-06-16)
When the host must live in the **stage's own VPC** (UAT isolation), not shared infra:
- Define it in `lower/<stage>/services` via the **fleet ec2-map** (`ec2.tf` + `variables_custom.tf` + `terraform.tfvars` ec2 map), which the CyberArk migration (COEXT-105281) added to test/services. data.tf already has core VPC/subnets/route53/prefix_lists there.
- **Naming**: the stage `project_prefix` includes the stage (e.g. `aws0caatest`), so key `bld01` → `aws0caatestbld01` (the FIRST build host *in that stage*; `bld02` only applies in infra where `bld01` is taken). Build nodes are all `bld` (per Markuss). IMPORTANT: `${project_prefix}eks*` in the stage = `aws0caatesteks*` (NOT `${project_prefix}testeks*`).
- **KEY-COLLISION (critical):** eis-eks builds the access-entry key as `regex("${ec2_group}[0-9]+", arn)`. `ci={ec2_group="bld"}` resolves BOTH the new `aws0caatestbld01` and the shared infra `aws0caabld01` → both → key `bld01` → duplicate-key plan FAIL. Fix: set the stage's `ci` mapping `ec2_group="testbld"` (resolves only the in-stage host, key `ci-testbld01`; drops shared infra bld01 from the stage cluster = isolation). If the host is already live when you hit this, switching ci→testbld is just an access-entry swap (no host churn).
- **IAM**: a GROUP `bld` policy (`enable_policy=true`) renders the stray test `files/iam/ec2/bld.json` which refs `${dns_zone}` (unsupplied by the group templatefile → tflint/plan fail). Use `custom_policy=true` on the ec2-map entry + a per-instance `files/iam/ec2/bld01.json` → `aws0caatestbld01-Policy` (UAT-scoped to `${project_prefix}eks*`).
- **DNS name** of the in-stage host = `<key>.<stage_private_zone>`. The eis-ec2 ec2-map sets `route53_zone_name = data.aws_route53_zone.stage_private.name`, and the test core creates the stage private zone `<stage>.aws<region>.<domain>` (`create_stage_zone`). So the CAA UAT build host resolves at **`aws0caatestbld01.test.aws0.caa-eis.cloud`** (A → private IP, e.g. 10.34.88.59) — NOT the infra zone. The OLD shared `aws0caabld01.infra.aws0.caa-eis.cloud` is a *different* host whose access to the stage cluster was deliberately dropped (the `testbld` matcher excludes it) → it now 401s on the UAT cluster. When someone asks "what's the DNS name of the build host", give the in-stage FQDN and explain the infra host is no longer authorized.

## Ansible bld-node config (Docker runner) — gotchas
Run `projects/aws/<client>/ansible/docker/run.sh playbook playbooks/<pb>.yaml --limit <host> --become` with `VAULT_TOKEN=$(cat ~/.vault-token)` (validate via curl `…/v1/auth/token/lookup-self`) + `AWS_PROFILE`. Playbooks for a bld node: `environment`, `docker_install`, `linux_joindomain`. **`vault_agent_ssl` is N/A for build hosts** (no TLS endpoint; shared bld01 has vault-agent inactive). The host is Acronym=`bld` → uses existing `group_vars/bld.yaml` + `linux_joindomain hosts: bld,jnk` (no new group_vars/host needed).
- **Image gaps** (add to `ansible/docker/Dockerfile`): `passlib` (else `environment` user-hash task fails "passlib must be installed") and `community.docker` (else `docker_install` errors `community.docker.docker_login` unresolved). This file IS tracked in the consuming ansible repo → normal MR there.
- **Order**: run `linux_joindomain` (AD join) BEFORE `docker_install` — `docker_install` adds the AD user `caa_build` to the docker group, which requires it to resolve. The ansible `user` module CAN'T add an AD-only user to a LOCAL group (usermod needs /etc/passwd). Quick fix: `gpasswd -a caa_build docker`. **Durable role fix** (`docker_install/tasks/users.yml`): `getent group docker` + `gpasswd -a {{item}} docker` loop over `docker_users` with idempotent check `item not in getent_group.docker[2]|split(',')`.
- **Roles are VENDORED** — `roles/.gitignore`=`/*` (only `local*`+requirements.yml tracked); each role pulled from `cv-devops/ansible/ansible-roles/<role>.git` via `roles/requirements.yml` (pinned, e.g. docker_install v1.1.0). Editing the vendored copy is ephemeral. To persist a role fix you're Reporter-only on cv-devops → mirror to `iac/ansible/roles/<role>` (Maintainer), tag the next patch, bump the requirements.yml pin (vault_agent_ssl v1.1.1 / COEXT-104228 precedent). **Test the SHIPPED path (not the local edit):** `rm -rf roles/<role>` then `./docker/run.sh exec ansible-galaxy install -r roles/requirements.yml -p roles/` → confirm `roles/<role>/meta/.galaxy_install_info` shows the new tag (proves the mirror+pin resolve), then run the playbook clean-room (e.g. `gpasswd -d <user> <grp>` first) and verify the pristine role does the fix.
- Verify: `systemctl is-active docker sssd`, `getent group docker` (incl. caa_build), `ls /etc/sudoers.d | grep <grp>_<client>_ssh`, `docker run --rm hello-world` PASS, registry login in `/root/.docker/config.json`.
