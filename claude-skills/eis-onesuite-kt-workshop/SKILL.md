# OneSuite provisioning KT workshop

The platform team is a **service provider**: it lays the paved road, the change team drives it. The
workshop series exists so a change team can independently provision a client's **lower** environments
(dev + test + shared services) using the same templates, Atlantis and ArgoCD the platform team uses.
It is delivered by **provisioning a real client env live** — the teaching artifact is production.

## Format that worked

- ~2h per session, one per phase-cluster, 2–4 days apart.
- **The expert drives and the session is recorded**; the learners reproduce it afterwards from the
  recording + wiki. (Tried the reverse in AFA #1 — handing the keyboard to a learner mid-session — and
  the group explicitly reverted: too slow, and the failures teach less when nobody can debug them.)
- Follow-ups land in Slack, not in the meeting.
- Every session ends with a wiki-update action for whatever broke.

## Session arc (maps 1:1 to `eis-onesuite-platform-provision` phases)

| Session | Phases | What is actually done live |
|---|---|---|
| #1 | P0 + P2 | Architecture + client inputs; toolchain install; `copier copy` the terraform client template; create the GitLab project; branch + MR; Atlantis webhook; first (red) plan |
| #2 | P3 + P4 | `atlantis apply` in order: infra bootstrap → infra core → infra services → dev core → dev services |
| #3 | P5 | Ansible repo from the ansible client template; Vault secrets; `.env` + container image; playbooks per host; CI/CD-team handoff package; (optionally) the Atlantis cutover |
| #4 | P6 | ArgoCD onboarding of `<prefix>deveks01` into the hub; MR; pipeline; app-of-apps sync |
| #5 | P8 | End-to-end verification + handoff (`eis-onesuite-e2e-verify`) |

## Pre-flight gates — check these the DAY BEFORE, each one has cost a live session

1. **Red Hat Cloud Access.** The new AWS account must be added to the EIS Red Hat subscriptions
   **before** `lower/infra/services` applies, or every RHEL EC2 fails. Owner is outside the team; chase
   on Slack. (AFA #2 lost the first half-hour to this; the group worked around it by applying
   `lower/dev/core` — which has no EC2 — while waiting.) See [[redhat-cloud-access-account-gate]].
2. **Post-bootstrap secret grant.** `lower-dev-services` plans die on `GetSecretValue` for the RDS
   secret unless the Atlantis plan role's `state_access.json` grants `${project_prefix}*/*`. Fixed in
   client template **v2.6.0**; a v2.5.0-rendered repo needs the bump or the one-line MR. See
   [[atlantis-plan-role-cannot-read-secrets]].
3. **Vault secrets for the Ansible session.** Missing secrets are the #1 cause of a dead P5 session.
   Copy the set from an existing client project and diff; automation passwords are generated by hand
   (password manager); the `atlantis` secret is created **by** the playbook, not before it.
4. **The seven silent scaffold gates** — HTTPS singular-`template` copier URL, local `pre-commit
   install`, instance runners disabled, the Vault entry named **`GitLab webhook secret`** (not the
   PAT), scaffold on a branch not `main`, regenerated `atlantis.yaml`, `git add` before pre-commit
   passes. Full list: [[onesuite-scaffold-silent-gates]] + skill `eis-onesuite-phase2-terraform-scaffold`.
5. **DNS delegation ticket** for the client's Atlantis URL — file it weeks early; it gates the
   cutover session. Route it to the **JCP/IT support** queue (US timezone, fast turnaround).
6. **Template pin.** Check the client template's latest tag the morning of the session; renovate will
   otherwise open the bump MR mid-workshop and confuse everyone.

## Standing answers (the change team asks these every time)

- **"Why are the EC2 toolchain hosts in `infra`, not `dev`?"** Escrow: production environments get
  handed to the client, and the shared toolchain must not go with them. Plus access isolation and
  per-account cost tracking.
- **"Why is there no `dev` in the shared-services host names?"** DNS length — `<prefix>` already
  carries region+project; adding a stage would make the FQDNs unmanageable. Shared services are
  deliberately stage-less because dev and test share them.
- **"Does every client need its own Nexus / OpenGrok / analytics?"** No. CAA shares them between dev
  and test to cut instance count; other clients get dedicated ones. It is a per-client decision.
- **"Where are the CloudWatch alarms?"** There are none in the Terraform stack. Lower environments are
  covered by **Prometheus + Grafana** (observascope, via ArgoCD); upper environments by **Datadog**.
  Standalone-EC2 monitoring is the observability owner's call — ask, don't invent. See
  [[eis-platform-standing-answers]].
- **"Who approves merge requests?"** GitLab **CE cannot enforce named approvers**, so the two-person
  review is a **convention**. What IS enforced: Atlantis `apply_requirements: [approved, undiverged]`
  on both the shared and the client Atlantis — an unapproved MR cannot apply. Pipeline checks are the
  only path to real enforcement in CE.
- **"Why only power-user, not admin, on the client account?"** Manual console changes create Terraform
  drift. Admin is granted through the `cloud-platform-admin` group when there's a reason.
- **"Why did my first plan fail?"** `services` depends on `core`, `core` on `bootstrap`. Red plans on
  the first MR are expected; only a red plan **after** its dependencies are applied is real.
- **"Which commit message?"** `type(scope): TICKET-123 - message` — the **space around the hyphen is
  required** by the lint, and `ci` is not an allowed type.

## After the session

- Update the wiki for whatever broke — that is the deliverable the change team actually reuses.
- File the follow-ups as named actions with an owner; unowned "the group will…" items don't happen.
- Save the Gemini notes doc locally (AFA series: `~/afa/workshop-notes/`) and record the delta against
  live state — the notes are ASR-derived and mis-transcribe names (`aws02` → "alpha", Selenoid →
  "Solenoid", OpenGrok → "Grog", IaC cluster → "IC cluster"). Verify every claim before acting on it.
